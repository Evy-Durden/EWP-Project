\subsubsection{Python pyproject.toml File}

The pyproject.toml file is a configuration file for Python packaging. It acts as the build system, dependency manager and handles tool configurations which are represented by three tables within in the file respectively \footnote{pyproject.toml specification. [online] homepage: packaging.python.org URL: https://packaging.python.org/en/latest/specifications/pyproject-toml/\#pyproject-toml-spec [Accessed 10.01.2026]}. Setuptools is the standard build system for Python projects \footnote{Ian Currie. How to Manage Python Projects With pyproject.toml. [online] homepage: realpython.com URL: https://realpython.com/python-pyproject-toml/ [Accessed 10.01.2026]}.

\begin{lstlisting}[language=bash,caption={pyproject.toml file}]
[build-system]
requires = ["setuptools"]
build-backend = "setuptools.build_meta"

[project]
name = "linux-analyzer"
version = "0.1.0"
description = "Misconfiguration scanner for Linux"
dependencies = [
    "typer"
]

[project.scripts]
linux-analyzer = "linux_analyzer.cli.main:main"

[tool.setuptools.packages.find]
where = ["src"]
\end{lstlisting}

This chapter is designed to be a high level explanation of the code structure.

\subsubsection{Main Modules/Files}

\textbf{core/ - Application Core}: Its role is to facilitate central coordination and logic and its key responsibilities are to orchestrate the analysis execution, manage execution context, defining the actual domain models  and enforcing dependency direction (hexagonal architecture).\newline

\textbf{ports/ - Architectural Interfaces (Ports)}: It defines the required capabilities, specifically  all the interfaces (ports) which are required by the core application logic. A critical distinction is worth mentioning here. The interfaces describe what the systems needs to. However they do not specify hot it is done. Adapters are part of other modules which implement these interfaces. The reason behind this that it enforces inversion of control. The goal is to ensure that  dependencies always point inwards toward the core.\newline

\textbf{analysis/ - Analysis Strategies}: Here the execution model is selected. It implements the Strategy Pattern to support multiple analysis models. \newline

\textbf{checks/ - Static System Inspection}: This module performs static inspection of the system state. Its role is to simply collect factual data about the system configuration, crucially without interpreting or evaluating any security implications. Its job is to collect raw facts without providing any insight or meaning.\newline

\textbf{evaluation/ - Static Interpretation}: Here the raw findings produced by the static checks are evaluated and transforms them into security-relevant assessments. Moreover it assign severity and risk levels to the findings.\newline

\textbf{runtime/ - Behavioral Analysis (eBPF)}: Its role is to implement the dynamic runtime monitoring by using eBPF-based runtime observation. It needs to load and manage eBPF programs, collect runtime event streams and detect behavioral patterns. This module is particulary privileged and as a consequence needs to be strictly isolated and controlled.\newline

\textbf{intelligence/ - Vulnerability Intelligence}: It communicates with CVE APIs to intergrate vulnerability intelligence sources. Furthermore it maps system findings to known vulnerabilities. \newline

\textbf{reporting/ - Reporting \& Output}: This module take care of the presentation of the results and findings of the analysis. It supports multiple output targets such as console output and a persistent report (report.txt).\newline

\textbf{privilege/ - Least-Privilege Enforcement}: It is responsible for privilege management as well as enforement which means detecting privilege levels and enforcing privilege boundaries.\newline

\textbf{system/ - System Interaction Abstractions}: It provides safe operating system interaction wrappers as controlled abstractions are needed for interacting with underlying operating system.\newline

\textbf{logging/ - Secure Logging}: Here the logging configuration and behaviour is centralized. It ensures that logs are useful for debugging and auditing without leaking sensitive system information.\newline

\textbf{config/ - Configuration Management}: Its key responsibilities include defining default configuration values and validating configuration inputs. It also manages the runtime configuration state.\newline

\textbf{errors/ - Error Taxonomy}: Its role is to define an explicit error classification. This is where custom exception types are defined and consistent error propagation is supported.\newline

\textbf{utils/ - Shared Utilities}: It provides reusable helper functions. Its main goal is to avoid duplication.


\subsubsection{Entry point of the application}

The entry point of the application is the CLI. As this is a CLI tool all user interaction will be handled through it by using the appropriate flags. The CLI is responsible for parsing input, validating options, and dispatching execution to the corresponding internal commands.

\subsection{Key Components}

\subsubsection{CLI}

It serves as the entry point of the application, specifically the main.py file. The user interacts with application over the CLI. It is comprised of four files to adhere to the principle of separation of concern. main.py sole responsibility is to start up the CLI. menu.py handles what happens when a user chooses a menu option. prompts.py takes care of the user input and is responsible for syntactic validation. output.py is the representation layer. It determines how things look across the entire CLI. 

\begin{lstlisting}[language=python,caption={entry point: main.py file}]
import typer
from .menu import show_menu

# creating a typer app
app = typer.Typer()

@app.command()
def main():
	"""
	The @app.command() decorator turns a function into a CLI command.
	Main simple calls into menu.py and does not implement any menu logic itself.
	The reason is separation of concern for testability, readability and maintainability.
	"""
	show_menu()
	
# ensure that code is only run when script is executed and not when it is imported
if __name__ == "__main__":
	app()
\end{lstlisting}

\subsubsection{Analysis Interface}

Its purpose is to implement the strategy pattern. It lays the foundation for being able to run multiple analysis types.

\subsubsection{Static Analysis}

It is divided in two distinct stages. The first stage of the analysis simply collects data about the system configuration. Afterwards in a separate process the findings from the first stage are evaluated and put into a security context.

\subsubsection{Behavioral Analysis}

It is the second type of analysis and uses eBPF programs to determine any runtime behavioral patterns.

\subsubsection{CVE Database Ports and Adapters}

This component adds intelligence from outside sources. If applicable it associates the findings with any known and well-documented vulnerabilities.

\subsubsection{Exceptions}

The goal is to handle the exceptions as part of the system architecture. They need to handled close to the boundary (point where the system must interact with something it does not control) where recovery or user communication is possible and not necessarily where the error occur. The error occurs somewhere in the system and the exception is raised there, however it is handled later after it propagated upward to a place where a meaningful decision can be made. \newline\newline Errors have to be distinguished and sorted into diverse categories. The reasoning behind this is that varying errors like user, system and programming erros require a different strategy for handling them.\newline\newline Custom exceptions help to improve readabilty and convey an explicit intent. Moreover they have a semantic component and document the specific failure states.\newline\newline It is crucial to design the exceptions in a security-sensitive way. There is a risk of information leakage which is addressed by sanitizing error information and keeping the messages intentionally minimal while is still providing clear und helpful information \newline\newline The overall objective of the exceptions strategy is to improve robustness, security, and maintainability.

\subsection{Security Aspects in Implementation}

This tool deals with very sensitive data. Therefore it is of the utmost importance to ensure security is a high priority and part of the whole development process, influencing architectural as well as implementation decisions.

\subsubsection{Defensive Validation}

The tool consumes untrusted and external data when the user is starting the tool. The user has to type in which mode to use and any applicable flags. User interaction is restricted to predefined menu options, which significantly reduces the attack surface. Input validation ensures only expected option values are processed.

\subsubsection{Input Sanitization}

The tool works with system-derived strings which are external and could be harmful. There is a chance a system could be under the control of an attacker. Potentially harmful are for example package names, version strings from package managers, OS command output, environment information, paths, usernames and hostnames. The policy is to treat all system-derived strings as untrusted.

\subsubsection{Encryption}

Data at rest is not encrypted. The tool does persist any sensitive data, therefore encryption of stored data is not required in this instance.\newline\newline Data in transit is in encrypted. All communication with external vulnerability databases is encrypted to ensure confidentiality and integrity of the transmitted data.

\subsubsection{Command Injection}

There are multiple strategies in place to combat command injection. As mentioned beforehand user interaction is restricted to predefined menu options. It is vital that commands are executed without invoking a shell (never use \textit{shell=True}) to prevent interpretation of injected metacharacters. Furthermore all values which are passed to subprocess calls have to be validated.

\subsubsection{Principle of Least Privilege}

The tool adheres to the principle of least privilege through various aspects. First and foremost its default is unprivileged execution and it only requests elevated privileges for checks that cannot be performed otherwise. Additionally privilege requirements are evaluated for each individual check rather than globally. Consequently the attack surface is minimized and risk of unintended system interaction is reduced.
